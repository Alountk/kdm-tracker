# App Shell Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the app's in-campaign chrome with the Stitch design's shell — a fixed top bar with the settlement's stat cluster, a fixed 4-tab bottom navigation, and the 11-step phase carousel.

**Architecture:** A new `ui/shell/` package holds the frame (`AppShell`) and its three parts. Tab selection is app-layer UI state beside the existing `Screen`, so `:core` is untouched. The tabs route to the screens that already exist, which are rebuilt 1:1 in later slices.

**Tech Stack:** Kotlin 2.3.21, Compose Multiplatform 1.12.1, Material 3, `kotlin.test` JVM suites.

**Spec:** `docs/superpowers/specs/2026-10-10-app-shell-design.md`

## Global Constraints

- **The render is the source of truth**, not the `designMd` prose: step 9's chip is `#8E1214`, not the prose's `#991b1b`; radii are 4dp/8dp, not 0.
- **Free tabs**: all four tabs navigate at any time; nothing is gated by phase.
- **The bar's title follows the selected tab**, not the record's phase. The record's phase only picks the initial tab. Lantern year and settlement name stay record-derived.
- **Copy is Spanish**, from the design: `Asentamiento`, `Supervivientes`, `Caza`, `Enfrentamiento`, `Secuencia de Fase Oficial`, `Paso N de 11`, and the carousel's short labels.
- **Render exactly, disable what is not implemented.** No faking: the unbacked chip shows `—` inert.
- **The shell is only for an in-campaign screen.** `Home` and `Account` keep the existing chrome and never show the bottom nav.
- **All shell glyphs are already bundled** in the subset (`fort`, `shield_person`, `explore`, `swords`, `group_add`, `account_balance`, `emergency`, `hourglass_empty`, `skull`, `check_box_outline_blank`, `handyman`, `shield`, `edit_note`, `flare`, `group`, `person`, `light_mode`) — use `KdmSymbols.glyph(name)`; never add a dependency.
- Run `./gradlew spotlessApply` before every commit (120 columns, no unused imports). Conventional Commits, no AI attribution.

## Review Focus

The failure modes the spec implies but its prose does not exercise, each pinned by a test in its owning task:

1. **A tab whose phase has not started** — tapping Caza while the record sits in the Settlement phase must resolve to the hunt view. *What is testable here* is that the tab resolves and the shell accepts it **independently of the phase** (Task 1's mapping test); the hunt view's own empty state is the Hunt screen's concern and is checked in Task 5's visual pass.
2. **Zero stats** — a settlement with 0 deaths must still render all three chips, showing `0`, not an empty cluster.
3. **An out-of-range active step** — the carousel must not crash when the record's step is outside `1..11`.
4. **Home and Account** — neither may render the shell, and neither may show the bottom nav.
5. **Exactly one active tab** — for any in-campaign screen, exactly one tab is active.

- [ ] **Step 3: Implement the frame.**

`inShell` is `ShellTab.of(screen) != null`. `AppShell` stacks `ShellTopBar` (title = the tab's `label`), the content in a `Modifier.weight(1f)` slot, and `ShellBottomNav`; it shows `PhaseCarousel` above the content only when `tab == ShellTab.SETTLEMENT`, and applies the bars' padding so content is never hidden.

- [ ] **Step 4: Add the navigation entry point, and open a campaign on the phase's tab.**

Add `fun show(screen: Screen)` to `LanternYearViewModel` (delegating to the controller and clearing `actionError`), and route the existing open/close-account paths through it. Then make `select(campaignId)` open the campaign on **the tab its phase implies**: `show(ShellTab.initialFor(record.phase).screen)`. Without this the phase→tab rule is dead code.
